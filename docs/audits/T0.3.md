# Audit — T0.3 "Schema wave 1 + constraint tests" (commit `4ac2d17`)

Read-only audit session. No repository file was changed. Spec sections were read
verbatim and expectations written down before the diff was opened, per the audit
procedure in `docs/agent-work-plan.md` §7.

---

## What this card was supposed to deliver, in plain terms

The card creates the **first sixteen database tables** — the storage for accounts,
billing, the connected shop domain, the ingestion pipeline's progress, the caches,
and the notification/email plumbing. It also creates a **repository layer**: a thin
set of functions that are the only sanctioned way to reach those tables, each of
which must be told which customer account it is acting for. And it adds **constraint
tests**: tests that try to write bad data and prove the database itself refuses.

Three things make this card worth auditing carefully.

1. Two product rules are supposed to become physically impossible to break here,
   not merely discouraged: **one shop domain per account and one account per shop
   domain**, and **a notification or email can never be sent twice** even when a
   background worker retries.
2. The **account-scoping rule** — every database query must name the account whose
   data it touches — is the whole of the product's data isolation. There are no
   teams and no sharing, so "did we filter by account" is the only thing standing
   between one merchant and another merchant's data.
3. This card's tables are the foundation every later card builds on. A wrong shape
   here is expensive later.

---

## Verification I actually ran

- `pnpm vitest run packages/db` — **21 constraint tests pass**, matching the commit
  message's claim, against the local Postgres 16.
- **Mutation test (the tests' teeth).** In a throwaway copy of the package outside
  the repo, I weakened four of the database constraints (turned the unique indexes
  on `domains.domain_normalized`, `notifications`, `email_sends` and the global
  kill-switch flag into ordinary non-unique indexes) and re-ran the suite. Seven
  tests failed, each naming the right rule. The tests are not decorative — they
  detect the constraint actually going missing.
- **Silent-skip test.** Pointed the suite at a dead database address. It failed
  loudly with `No Postgres at the test URL. Constraint tests cannot be skipped
  silently — run pnpm db:up first.` rather than reporting green on zero assertions.
- **Compile-time proof test.** The card's other done-when is "a repository call
  without scope fails to compile". In the same throwaway copy I removed the marker
  that makes an account scope unforgeable; `tsc` then failed with
  `Unused '@ts-expect-error' directive`. The proof file is wired into
  `pnpm typecheck` and cannot rot silently.

## The flagged concern: the five-table exemption from account scoping

**Short answer: the exemption is substantively correct for all five tables — but
the single sentence given as its justification is only true of three of them, and
the stated count of five is wrong; a sixth table is reached the same way.** This is
a reasoning-and-documentation defect, not a data-isolation hole. No table that
holds one merchant's data is exempt.

The justification written in `packages/db/src/scope.ts:24-26` is: *"Each is written
before an account is known."* Taken one table at a time:

| Table | What writes it, and when | Is the exemption genuinely necessary? | Does the stated reason fit? |
|---|---|---|---|
| `stripe_events` | The Stripe billing webhook receiver, the instant an event arrives. It is stored and answered `200` before anything looks at it; a background worker figures out later which customer it concerns (tech §3). | **Yes.** The account is genuinely unknown at write time. | Yes |
| `webhook_events` | The Shopify webhook receiver, likewise: verify the signature, store, return `200`, process later (tech §3, main §14.3.8). | **Yes.** Technically the shop name arrives in a request header and could be looked up — but the spec explicitly requires storing before routing, so this is spec-mandated, not merely convenient. | Yes |
| `preview_cache` | The public, logged-out "show me a preview of your store" endpoint (main §3.2). | **Yes**, and emphatically: there is no account and never will be. Adding an `account_id` here would work against the rule that preview output is disposable and never feeds the real product. | Yes |
| `request_cache` | The wrapper around paid outside calls (search-data vendor, the language model), written the moment a response arrives. | **Yes — for a different reason.** The account is perfectly well known: a background job for a specific merchant made the call. It has no account column because the cache is *deliberately shared across merchants*: the spec's own end-to-end test asserts "billable-call count equals the number of **distinct** canonical requests" (main §14.3.9), which only holds if two merchants asking the same question pay for one answer. | **No** |
| `email_suppressions` | The email vendor's bounce/complaint webhook. Keyed by email address. | **Yes — again for a different reason.** A hard-bounced address must stay suppressed no matter which account tries to reach it (tech §1.5). And the account *is* resolvable: `accounts.email` is unique, so one lookup would find it. | **No** |

Two further precision problems:

- **It is six tables, not five.** `ops_flags` — the kill-switch table — is also read
  through the same system-level escape hatch (`isGlobalFlagActive` in
  `packages/db/src/repositories/system.ts:104`). That table *does* have an
  `account_id` column. The specific query is safe (it pins `scope = 'global'`, and
  a check constraint guarantees a global flag has no account), but a reviewer
  grepping for the escape hatch will find six tables where the comment promises five.
- **One of the five is not actually used.** `email_suppressions` appears on the list
  but has no repository function in this commit at all. Four of the five are
  genuinely exercised.

Worth noting in the code's favour: the `DECISIONS.md` entry for this choice
(2026-08-27, T0.3) gives the four *distinct* correct reasons, and the schema file's
own comment on `email_suppressions` gets it right too. It is only the `scope.ts`
comment — the one a future engineer will read when they want to add a seventh table
to the list — that flattens them into one story. That is the version that will be
used to justify the next exemption.

## Findings

Format: `[severity] §ref — finding / spec requires / code does / proposed fix`

---

`[major]` **CLAUDE.md code-structure rules; tech §3** — *The account-scoping guarantee
is bypassable by design, and the very next card already bypasses it.* /
**Spec requires:** "Every repository method requires an `accountId` scope parameter;
there is no unscoped table access outside migrations and admin scripts" (CLAUDE.md),
and "every query is `WHERE account_id = session.account_id`, enforced by a repository
layer" (tech §3). /
**Code does:** The scope check is real but narrow — it guards the *three repository
files this card wrote*. `packages/db/src/index.ts` simultaneously re-exports every raw
table object and the raw database handle, so `db.select().from(notifications)` — no
account named — compiles anywhere outside a route handler, with no lint rule against
it. This is not hypothetical: `packages/jobs/src/runtime/steps.ts` (written by the
*next* card, T0.4) already queries `job_steps` and `ingestion_jobs` directly with no
scope object anywhere. A contributing cause is that `job_steps` has no `account_id`
column of its own — correctly, per main §13, it hangs off `ingestion_jobs` — and this
card supplied no helper for scoping through that link, so the next card went around
the layer rather than through it. The card's own done-when ("a repository call without
scope fails to compile") is *satisfied*; the constitution's rule is not. /
**Proposed fix:** decide which of these you want, then have the integrator card it:
(a) stop the `@sortiva/db` package exporting raw tables and the database handle —
make repositories the only public surface, with an internal path for the package's
own use; (b) add a lint rule forbidding imports of the schema barrel outside
`packages/db`; (c) add the missing join-scoped helpers (`findJobStepsForAccount`
etc.) so T0.4 has a sanctioned route. (a)+(c) is the durable pair; (b) alone is the
cheap stopgap. Either way this belongs on the T10.2 invariant sweep as a named gap.

---

`[minor]` **`packages/db/src/scope.ts:20-31`; main §14.3.6, §14.3.9; tech §1.5** —
*The justification for the account-scoping exemption is a single story that fits
three of the five tables.* /
**Spec requires:** nothing directly — this is a reasoning defect in a comment that
will govern future decisions. /
**Code does:** says all five exempt tables are "written before an account is known".
True for `stripe_events`, `webhook_events`, `preview_cache`. False for
`request_cache` (the account is known; the table is deliberately shared across
merchants so a repeated paid query is billed once — main §14.3.9) and
`email_suppressions` (the account is resolvable; suppression is global by nature —
tech §1.5). Also says "five tables"; `ops_flags` is a sixth reached the same way. /
**Proposed fix:** rewrite that comment to give each table its own one-line reason,
and state the standing rule the list must satisfy — *a table may be exempt only if
it has no `account_id` column in main §13* — so the next candidate is tested against
a criterion rather than against a precedent. Mention `ops_flags` explicitly as the
account-bearing exception, read only through a `scope = 'global'` filter.

---

`[minor]` **main §14.3.6** — *An undocumented consequence of the shared cache: one
merchant can be served another merchant's cached language-model answer.* /
**Spec requires:** the cache is keyed on `(prompt_version, model_id,
sha256(rendered_prompt))` and shared, so that retries and repeats do not re-bill. /
**Code does:** exactly that, correctly. But the property nobody has written down is
that two accounts producing a byte-identical prompt share a stored completion. In
practice an identical prompt implies identical inputs, so the practical leak is
near-zero — but it is a cross-tenant data path that exists on purpose and is
recorded nowhere. /
**Proposed fix:** no code change. Add one line to the `request_cache` comment and to
`DECISIONS.md` stating that the cache is intentionally cross-tenant and why, so the
next person to add a cached call type knows to check that its prompt cannot encode
one merchant's private data in a form another merchant could reproduce.

---

`[minor]` **main §5** — *Claiming a domain cannot report which of three things went
wrong.* /
**Spec requires:** three distinct outcomes. Domain already claimed by someone else →
the exact error string "This domain is already connected to another account…".
Claimed by this account → silent no-op, redirect to dashboard. (And implicitly:
this account already has a *different* domain → a third thing entirely.) /
**Code does:** `claimDomain` (`packages/db/src/repositories/domains.ts:20`) uses
`ON CONFLICT DO NOTHING` and returns `undefined` for all three. The database
behaviour is right — the race is genuinely impossible — but the caller (T1.4, not
yet written) cannot tell a squatter from a returning user without a second query. /
**Proposed fix:** have `claimDomain` return a discriminated result
(`claimed` | `already_yours` | `taken_by_other` | `account_has_other_domain`),
determined by reading back the conflicting row inside the same transaction. Cheap
now, and it stops T1.4 inventing its own follow-up read.

---

`[minor]` **tech §1.5; main §14.6** — *The email table cannot record an
account-deletion confirmation.* /
**Spec requires:** suppressed addresses skip the queue "except for account-security
email (deletion confirmation)" — so such an email exists and must be sendable. /
**Code does:** `email_sends.type` reuses the fifteen-value notification enum from
tech §1.2, which is a list of *bell notifications* and contains no security or
deletion type. The email pipeline therefore has no value to stamp on that send,
and no row to make it exactly-once. /
**Proposed fix:** either give `email_sends` its own enum that is a superset of the
notification types (adding `account_deletion_confirmation`, and whatever else the
security path needs), or add the security types to the shared enum and accept that
some values are email-only. Flag it to the spec keepers too — tech §1.2's enum is
described as matching the UI notification matrix, and this email is not a matrix row.

---

`[minor]` **main §14.6** — *`domains.release_after` is a column with nothing behind
it.* /
**Spec requires:** on account deletion, the domain claim is "released after a 7-day
grace window" so a squatter cannot take it the same hour. /
**Code does:** adds the timestamp column, but the unique index on
`domain_normalized` is unconditional. A row whose `release_after` is long past still
blocks anyone else claiming that domain. The column's comment says a later card
(T8.3) will delete the row — in which case the timestamp is an audit note, not a
mechanism. The same shape applies to `shopify_conns.invalidated_at` versus the
unconditional unique index on `shop_handle`: a revoked Shopify connection still
blocks that shop from being connected by a different account. /
**Proposed fix:** decide now which it is, and write it down. Either the sweep hard-
deletes (then say so in the column comment and drop the pretence that the column
enforces anything), or make the unique indexes partial —
`WHERE release_after IS NULL` / `WHERE invalidated_at IS NULL` — which makes the
release real at the database level. The second is the version that survives a sweep
job failing to run.

`[minor]` **`docs/agent-work-plan.md` §6, T0.3 scope line** — *Four of the twelve
unique indexes have no test.* /
**Spec requires:** the card's scope says "tests proving each unique/partial index
fires". Its done-when names four specific cases. /
**Code does:** the four named cases all pass, plus four more. Untested:
`accounts_stripe_customer_id_key` (one Stripe customer per account),
`shopify_conns_shop_handle_key` (one shop, one account),
`ingestion_jobs_account_run_key` (one ingestion run per account per run id), and the
`subscriptions` primary key (one subscription row per account). /
**Proposed fix:** four more short tests in the existing file, same shape as the ones
there. Low effort, and it closes the gap between what the scope line promises and
what CI proves.

`[nit]` **`packages/db/src/constraints.test.ts:296`** — *A test name claims twice
what the test checks.* /
**Spec requires:** n/a. /
**Code does:** the test named "keeps one subscription row per account **and** one per
Stripe subscription" only exercises the Stripe-subscription-id half; it inserts the
two rows under two different accounts, so the per-account primary key is never
challenged. /
**Proposed fix:** add the second insert under the same account, or rename the test.

---

`[nit]` **tech §1.5** — *`'unsubscribed'` is offered as a suppression reason, but
unsubscribing is not suppression.* /
**Spec requires:** bounce and complaint webhooks write suppressions; a one-click
unsubscribe "flips the corresponding preference". Different mechanisms with
different consequences — a suppression blocks *all* mail to that address, a
preference blocks one category. /
**Code does:** the `email_suppression_reason` enum carries a third value,
`unsubscribed`, that the spec does not create. Harmless today, but it invites the
send worker to record an unsubscribe as a suppression, which would silently stop
transactional mail (connection lost, payment failed) to a merchant who only opted
out of one digest. /
**Proposed fix:** drop the value in the next schema wave, or add a comment stating
it is reserved and that unsubscribe must never write this table.

---

`[nit]` **main §13, §14.3.8** — *Two webhook providers share one identifier
namespace.* /
**Spec requires:** `webhook_events.webhook_id` unique, insert-or-ignore. /
**Code does:** exactly that — but this commit also routes the email vendor's
webhooks into the same table via a new `source` column, while leaving identity on
`webhook_id` alone. Shopify's UUIDs and Resend's `msg_*` ids will not collide in
practice, so this is a theoretical point. The `DECISIONS.md` entry defends the
single-column key as "exactly as §13 states", which is true but beside the point:
§13 only ever contemplated one source. /
**Proposed fix:** make the key `(source, webhook_id)` in a later wave, or note in
`DECISIONS.md` that the collision risk was considered and accepted.

---

`[nit]` **main §9.4** — *Every account will publish on a UTC clock until T2.5 lands.* /
**Spec requires:** the account's timezone defaults from the persona's country. /
**Code does:** `account_settings.timezone` defaults to `'UTC'`, with a comment saying
T2.5 will derive the real value. Correct as a database default — the persona does
not exist when the settings row is created — but until T2.5 ships, the 09:00 publish
hour means 09:00 UTC for a German merchant. /
**Proposed fix:** none needed in this card. Just make sure T2.5's done-when includes
back-filling existing rows, not only setting the value for new ones.

## What is clean, and worth saying so

- **Invariant 1 (one domain per account, one account per domain)** — enforced by two
  unique indexes in the database, claimed with an insert-and-catch-the-conflict, not
  a check-then-insert. Proven by test, and I confirmed by mutation that removing
  either index makes the tests fail. This is exactly what the constitution asks for.
- **Invariant 26, first half (a notification or email can never be sent twice)** —
  the unique key on (account, type, dedupe key) is present on both tables, and the
  dedupe-key column is `NOT NULL`. That last choice is right and non-obvious:
  Postgres treats empty values as all different from each other in a unique index,
  so a nullable column would have silently switched the guarantee off for whichever
  notification type forgot to set a key. Mutation-verified.
- **Invariant 26, second half (attention items are live queries, never stored)** —
  satisfied by there being no attention-items table. Absence is the correct
  implementation here.
- **The test suite cannot pass by doing nothing.** The deliberate "fail loudly if
  there is no database" guard works — I verified it. This is the single most
  valuable thing in the commit, because the failure mode it prevents (a constraint
  suite that silently skips and reports green forever) is exactly how database
  invariants rot.
- **The compile-time scope proof has teeth**, verified by mutation. It is checked by
  `pnpm typecheck`, and it breaks the build if it ever stops proving anything.
- **All sixteen named tables exist** with the columns main §13 lists; every
  fixed-set column is a real database enum, so adding a value requires a migration —
  which is the friction tech §1.2 explicitly asks for.
- **Every undictated choice is journalled in `DECISIONS.md`**, and the
  account-scoping exemption is written up as *a contradiction with CLAUDE.md that
  the session is flagging rather than resolving* — which is the behaviour the
  constitution asks for, even though the shorthand version of the reasoning then
  leaked into the code comment.

---

## Bottom line

The card delivers what it promised, the two invariants it claims are genuinely
enforced by the database, and the tests that prove them are real tests that fail
when the constraints are removed. The flagged concern comes back **clean on
substance** — no table holding one merchant's data is exempt from scoping — but the
written justification is looser than the decision it defends, and should be tightened
before it is used to justify the next exemption.

The one finding worth acting on before more code lands on this foundation is the
`major`: the account-scoping rule is enforced on the repository functions but not on
the tables themselves, and the next card in the sequence has already gone around it.
That is a decision for you — how much you want to spend closing it now versus
carrying it to the M10 invariant sweep.
