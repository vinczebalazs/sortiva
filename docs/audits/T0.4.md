# Audit — T0.4 "Worker runtime & step state machine" (commit 776d4b5)

Read-only audit session. No source file was changed. Spec sections were read and written up
before the diff was opened, per the brief.

## What this card built, in plain terms

Sortiva does its slow work — pulling a store's catalogue, summarising products, working out the
store's persona, finding keywords — in **background jobs** rather than while a person waits on a
web page. A background job can be delivered twice (the queue guarantees "at least once", never
"exactly once"), and the machine running it can die halfway. T0.4 is the plumbing that makes
that safe: a table of **steps** with a state each (waiting / running / done / failed), rules
about which step may start when, a way to record "I already did this" so a repeat delivery
doesn't do the work twice, a retry schedule, a **dead-letter queue** (a parking bay for work
that failed for good, so a human can look at it and press replay), and a lock that keeps all of
one store's work single-file.

No actual step is implemented yet — the nine steps exist as rows and names only. This card is
the machinery the later cards plug into. That matters for severity: several findings below are
cheap to fix now and expensive once eight lanes have built on top of them.

**Verification performed:** `pnpm test` — 361 tests, 18 files, all pass. `pnpm chaos` passes
(but see [blocker] below: the chaos suite currently contains only an empty scenario, so it
proves nothing yet). `pnpm typecheck` and `pnpm lint` clean.

## Findings

### The two flagged concerns

`[major] main §14.3.2 / §13 — the "already done this" record lives on the job rows themselves, and nothing protects them / spec requires that a worker seeing a completed idempotency key returns the stored result without executing ("the cache is the ledger"); §13 does put `idempotency_key` on `job_steps`, so this placement is spec-sanctioned, but the durability of that record is what makes the whole effectively-once guarantee real / code does `lookupCompletedKey` (packages/jobs/src/runtime/steps.ts:131) reads `job_steps WHERE idempotency_key = $1 AND state = 'succeeded'` — the ledger IS the step rows. `job_steps.job_id` cascades from `ingestion_jobs`, which cascades from `accounts` (packages/db/src/schema/jobs.ts:55, :30). I traced every current deletion path: **nothing in the repository today deletes `ingestion_jobs` or `job_steps` rows** other than the account cascade, and the daily retention sweep registered in the crontab (packages/jobs/src/runtime/crontab.ts:86) names only notifications, email_sends, webhook_events, request_cache and GSC rollups — not job rows. So the concern is *currently unrealised*: a replay today cannot re-execute completed work through this route. Three things make it a live risk rather than a closed one: (1) the retention sweep is a registered cron entry **with no handler yet** — whoever writes it will be shopping for tables to prune, and nothing in the schema or a test says these rows are load-bearing; (2) `job_dlq.step_id` is declared `ON DELETE set null` (packages/db/migrations/0001_wave1_addendum_job_dlq.sql:20), which tells the next reader that deleting step rows is an anticipated event; (3) any future "restart onboarding" or "re-run ingestion" feature would naturally delete the old run. If a step row is deleted, the evidence that its work was done vanishes and a replay re-executes it for real — for `catalog_sync` that is a re-billed Shopify crawl, for `distill` a re-billed run of LLM calls. The authoring session flagged this honestly in DECISIONS (2026-08-27 T0.4, "with a known limit") — the flag is accurate; my judgement is that a documented convention is not enough teeth for an invariant / proposed fix cheapest option: add a test in `packages/db` asserting that the migration set contains no `ON DELETE cascade` reaching `job_steps` from anything a sweep would touch, plus a comment on `retention_sweep_daily`'s crontab entry naming `job_steps` as never-prunable. Structural option (recommended if run-pruning is ever likely): move the ledger to its own table keyed on `idempotency_key` with `output_ref`, no foreign key to jobs at all, so pruning runs cannot erase it. Founder call, because it is a schema-wave change.`

`[blocker] main §14.3.1 / tech §2.1 — a job killed mid-step is stranded forever, silently / spec requires "restarting a job just means re-dispatching non-succeeded steps" (§14.3.1), and tech §2.1 justifies running the worker inside the web server precisely on the grounds that "anything that doesn't finish resumes idempotently" / code does `dispatchableSteps` (packages/jobs/src/runtime/steps.ts:65,71) and `claimStep` (:120) both restrict themselves to states `pending` and `failed_retryable`. A step that was mid-flight when the process died stays in state `running` forever: the dispatcher will not offer it, and a worker that is handed it anyway returns `not_claimed` and exits quietly. There is no lease, no heartbeat, no timeout, no sweeper for stale `running` rows anywhere in the repository (I grepped for one). The store's onboarding stops with no error, no DLQ entry, and no user-visible signal. This is not theoretical: `catalog_sync` is specced at ~8 minutes for a 500-product store (§14.3.3), Railway's SIGTERM grace period on a deploy is far shorter, and after the grace period the process is killed outright — so an ordinary deploy landing during a catalogue sync strands that store. The card's own done-when says "a step crashed mid-checkpoint resumes at the cursor"; the test that claims it (packages/jobs/src/runtime/runtime.test.ts:418) simulates the crash by *throwing an exception*, which leaves the row in `failed_retryable` and does resume — the process-death case it is named for is untested and does not work. The chaos harness would catch it, but the chaos suite currently holds only an empty scenario (packages/jobs/src/chaos/harness.ts:190), so `pnpm chaos` passing means nothing here yet / proposed fix add a lease to the running state: stamp `started_at` (the column already exists) on claim, and either (a) let `dispatchableSteps` also offer `running` rows whose `started_at` is older than a per-step lease with `claimStep` guarding on the same, or (b) add a small "reap stale running steps" sweep to the crontab that moves them to `failed_retryable`. (a) is safe here because the per-account lock already prevents two live workers touching the same account. Either way, add a chaos scenario that kills the process mid-step rather than throwing, so this can never silently regress.`

`[major] main §14.3.3 / CLAUDE.md invariant 18 — the account lock is a different Postgres mechanism than the one specced, and it can leak / spec requires "All pipeline work for an account serializes through a per-account advisory lock (Postgres `pg_advisory_xact_lock(account_id)` **or equivalent**)"; CLAUDE.md invariant 18 names `pg_advisory_xact_lock(account_id)` without the escape hatch / code does uses the **session-scoped** lock `pg_advisory_lock` on a dedicated connection (packages/jobs/src/runtime/lock.ts:51), logged in DECISIONS. The rationale is sound and I agree with it: the transaction-scoped form would require one open transaction for the whole step, and §14.3.4 requires long steps to commit checkpoints as they go — a checkpoint you can only see after the step commits is not a checkpoint. So the substitution is *justified*. But the two mechanisms differ in exactly one property, and it is the dangerous one: the transaction-scoped lock is released by Postgres automatically at commit **or** rollback and cannot be leaked by any code path; the session-scoped one must be explicitly unlocked, or the connection must die. I traced every release path. Safe: normal return, handler throws (tested at runtime.test.ts:406), process crash or SIGKILL (Postgres releases session locks when the connection drops), SIGTERM drain. **Two paths are not safe.** (1) `pool.connect()` succeeds and then the `hashtext` query or the `pg_advisory_lock` query throws — lines 49–51 sit *outside* the `try/finally`, so the pooled connection is never returned. The lock was not acquired, so no store stalls, but the connection pool leaks a slot per occurrence; the pool is sized at 10 and is shared with the web server, so ten such errors take the whole app down. (2) The unlock query itself fails (line 58) — the `finally` still calls `client.release()` with no error argument, which returns the connection **to the pool while it still holds the lock**. `pg` does not reset session state on release. That store's lock is then held forever by a connection nobody knows is holding it: every future job for that store blocks indefinitely, with no error anywhere. The realistic trigger is a handler that uses the `lock.client` connection the interface hands it (packages/jobs/src/runtime/lock.ts:36) for a transaction that aborts — Postgres then refuses every subsequent command on that connection, including the unlock / proposed fix (i) move `pool.connect()` inside a `try` whose `finally` releases, so lines 49–51 cannot leak a connection; (ii) in `release`, catch the unlock failure and call `client.release(err)` with a truthy argument — that destroys the connection instead of pooling it, and Postgres frees the session lock the moment the backend disconnects. Both are small, local changes. Separately, ask the integrator to reconcile CLAUDE.md invariant 18's wording, which currently names a function the code deliberately does not use.`

`[major] main §14.3.3 — nesting the account lock deadlocks permanently, where the specced mechanism would not / spec requires only that account work serialises; it does not discuss nesting / code does each `withAccountLock` call takes a **fresh pool connection** (lock.ts:49), so a call nested inside another for the same account waits on a lock its own outer call holds — a self-deadlock with no timeout, blocking forever and parking two pool connections. The specced `pg_advisory_xact_lock` is re-entrant within one transaction and would simply succeed, so this hazard is created by the substitution, not inherited from the spec. The test at runtime.test.ts:398 proves the *non-blocking* variant returns undefined when nested — it documents the hazard without guarding the blocking one. Nothing nests today because no step handlers exist; every lane about to write one is the population at risk. Compounding this: there is no `lock_timeout`, so any hung lock-holder (not just a nested call) blocks all waiters indefinitely, and each waiter occupies one of the ten pool connections shared with the web server / proposed fix set a bounded `lock_timeout` on the lock connection before acquiring, so a wait fails loudly instead of hanging (the step then retries on the normal §14.3.5 backoff); and track held account locks in a process-local set so a nested acquisition for an account this process already holds throws a clear error instead of deadlocking.`

### Other findings

`[major] tech §2.1 — the shutdown signal that would let a long step stop cleanly has no producer / spec requires "Railway sends SIGTERM with a grace period on deploy; Graphile Worker drains gracefully" / code does `runStep` exposes `ctx.signal`, an abort signal a long loop is supposed to check so it can stop at a checkpoint during a drain (packages/jobs/src/runtime/runStep.ts:95–98, and the comment at :62 says "Aborted on graceful shutdown"). Nothing anywhere constructs that signal: `installSignalHandlers` calls `runner.stop()` and waits, and no caller passes `options.signal`. So the drain waits for the full step to finish on its own, and past Railway's grace period the process is killed — which is precisely the situation the blocker above turns into a permanent stall. Two halves of one mechanism, neither wired to the other / proposed fix have `bootstrapWorker` own an `AbortController`, abort it in the signal handler *before* awaiting `runner.stop()`, and pass its signal down to every `runStep` call, so a long step can save its cursor and return during the grace period.`

`[major] CLAUDE.md code-structure rules — the worker runtime reaches into database tables directly, bypassing the scoping discipline T0.3 built / spec requires (constitution, not the specs) "Every repository method requires an `accountId` scope parameter; there is no unscoped table access outside migrations and admin scripts." T0.3 implemented this as a branded `AccountScope` type that only `accountScope()` can produce, with a compile-time test proving it cannot be omitted (packages/db/src/scope.ts) / code does packages/jobs/src/runtime/steps.ts and dlq.ts query `jobSteps`, `ingestionJobs` and `jobDlq` directly through Drizzle with no scope at all — `getStep(db, stepId)`, `dispatchableSteps(db, jobId)`, `dlqDepth(db)`, `listOpenDlq(db)`, `replayDlqEntry(db, dlqId)`. There are no repositories for these tables in packages/db. No DECISIONS entry covers the deviation. Practically the risk is low (worker code, not request handlers, and `lookupCompletedKey`'s key already hashes the account id so it cannot cross accounts) but this is the first breach of a rule T0.3 spent real effort making unbreakable, and it sets the precedent every step-handler card will copy / proposed fix either add scoped repositories in packages/db for `ingestion_jobs`, `job_steps` and `job_dlq` and route the runtime through them, or log a DECISIONS entry stating that job-runtime tables are exempt and why. Founder/integrator call — my recommendation is the repositories, since the exemption is hard to bound.`

`[minor] CLAUDE.md migration rule — a migration was added outside a schema-wave card / spec requires "Migrations are added only by schema-wave cards. Feature cards that need a column file a DECISIONS entry and wait for the next wave, or negotiate with the integrator." / code does T0.4 adds `packages/db/migrations/0001_wave1_addendum_job_dlq.sql`, creating the `job_dlq` table. The card's done-when genuinely requires a DLQ ("DLQ entry carries step + key + error") and main §13 lists no table for it, so the work could not be done without it. The session filed a DECISIONS entry that names the rule and says it is breaking it, and left the resolution to the integrator — which is the behaviour the constitution asks for. Reporting it so the integrator's decision is explicit rather than assumed / proposed fix integrator folds `0001` into wave 1 or formally accepts it as a mini-wave; no code change.`

`[minor] main §14.3.1 — the checkpoint write is the one database write in this card that is not guarded / spec requires transitions to be guarded updates so a worker that has lost ownership of a step stops touching it / code does `saveCheckpoint` (packages/jobs/src/runtime/steps.ts:147) writes `UPDATE job_steps SET checkpoint = ... WHERE id = ?` with no state condition, so a stale worker can overwrite the live owner's cursor. Every other write in the file is guarded. In practice the account lock makes two same-account workers impossible, so this is defence-in-depth rather than a live bug — but the lock-leak path above is exactly the scenario where that assumption fails / proposed fix add `AND state = 'running'` to the checkpoint update and have a zero-row result surface as a lost-ownership error.`

`[minor] main §14.3.5 — a dead-letter entry whose step row is gone replays into nothing / spec requires "Ops can replay a DLQ item with one action because idempotency makes replay safe" / code does `replayDlqEntry` (packages/jobs/src/runtime/dlq.ts:~72) marks the entry replayed, then resets the step to `pending` **only if `stepId` is non-null**. Because `job_dlq.step_id` is `ON DELETE set null`, an entry that outlives its step silently becomes a replay button that does nothing: it reports success and no work is rescheduled / proposed fix return a distinguishable outcome (or throw) when `stepId` is null, so the operator sees "cannot replay: the step record is gone" rather than a false success.`

`[minor] main §14.3.3 — the lock key is a 32-bit hash of the account id, so unrelated stores can share a lock / spec requires per-account serialisation; cross-account work "fully parallel" / code does the key is `hashtext(account_id)::int` (lock.ts:26), a 32-bit space. Two different accounts collide with roughly 1% probability at 10,000 accounts and near-certainty in the low hundreds of thousands. The consequence is over-serialisation, not incorrect data: two stores queue behind each other. Safe, but it quietly erodes the "cross-account work is fully parallel" property, and it will be invisible when it happens / proposed fix use the single-bigint advisory-lock form with a 64-bit hash of the account id (`hashtextextended`), which removes the collision risk; the two-integer namespace is not needed for isolation, since Postgres keeps the one-key and two-key advisory lock spaces separate.`

`[minor] main §14.3.2 — the completed-key short-circuit is global across runs, and the correctness of every step now depends on a convention no code enforces / spec requires keys derived from inputs, with a per-step `input_version` definition (product `updated_at` + body checksum, sync generation number, and so on) / code does `deriveIdempotencyKey` correctly refuses an empty `input_version` and separates its three parts with a NUL byte so boundaries cannot shift — that part is right. But `lookupCompletedKey` matches **any** succeeded row with that key anywhere in the table, including from an earlier run. That is the intended §14.3.2 behaviour when the input really is unchanged. The hazard is that the runtime accepts any string as `input_version`: a later card that passes a constant for a waiting step like `oauth_wait` or `awaiting_confirmation` would make that step short-circuit to "already done" on every subsequent run, permanently. The doc comment hands the responsibility to "the step's owning card" with no check / proposed fix nothing to fix in this card; add the constraint to the step-handler cards' done-when, or have the runtime require each registered step to declare how its `input_version` is computed.`

`[nit] packages/db/src/testing.ts — the test-truncation list is now incomplete / code does `WAVE_1_TABLES` (line 77) does not include `job_dlq`. It is truncated anyway via `TRUNCATE ... CASCADE` from `accounts`, so no test is affected, but the list reads as authoritative and is no longer a full inventory / proposed fix add `job_dlq` to the list.`

`[nit] packages/jobs/package.json — `@sortiva/rules` is declared as a dependency and never imported / proposed fix drop it, or leave it if the step handlers are expected to need it imminently.`

### Things checked that are correct

Worth recording, since a clean result on a checked item is information:

- **Retry schedule.** 1m / 5m / 25m with jitter uniform in ±20%, three retries then dead-letter — matches §14.3.5 exactly. The attempt counter is incremented on claim and the arithmetic works out to one initial attempt plus three retries, which is what the spec means. Tested, including that the jitter actually reaches both ends of its range rather than being nominally random.
- **Guarded transitions.** Every state change except the checkpoint write is `UPDATE ... WHERE state IN (expected)`, returns `undefined` on zero rows, and callers stop. Tested with two concurrent workers racing for one step (invariants 15 and 18).
- **Step dependency graph.** The `gsc_connect` judgement call is right and matters: Search Console connection depends on keyword discovery but confirmation does **not** depend on Search Console, so a merchant who skips Google cannot get stuck in onboarding (§14.3.1's "never blocks `awaiting_confirmation`", §7.11 Limited Intelligence). A `skipped` step counts as satisfied. Tested, including a cycle check on the graph.
- **Failure classification.** Revoked-token errors route to the reconnect state rather than the dead-letter queue (§14.3.5, §6.2); an unrecognised error defaults to retryable, which is the correct side to err on under an at-least-once queue.
- **Crontab.** All thirteen recurring jobs tech §2 names are registered, each with the section that requires it. Two good calls: the worker **refuses to enable scheduling** until every scheduled job has a handler, so a cron entry pointing at nothing fails at startup instead of being discovered months later; and all schedules are UTC with per-account clock work explicitly resolved inside the task, so a German store cannot end up published to at 09:00 UTC (§9.4).
- **Graceful shutdown.** SIGTERM drains in-flight jobs and a second signal during a drain is ignored rather than starting a second stop. Verified against a real Graphile worker with a real in-flight job, not a mock.
- **Double-replay of a dead-letter entry** is a guarded update, so an operator double-clicking "replay" runs the work once.
- **In-process worker start** via `apps/web/instrumentation.ts` with a `WORKER_ENABLED=false` escape hatch, which is what makes the later split to a separate Railway service a config change rather than a code change (tech §2.1).
- **Per-suite test databases.** Each integration suite creates and migrates its own database, removing a class of parallel-test failures that look like constraint bugs and are not.
