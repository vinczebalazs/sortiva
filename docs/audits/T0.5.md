# Audit — T0.5 Provider wrappers (commit `c6cb4d3`)

Read-only audit. Nothing was changed. Spec sections were read cold and expectations written
before the diff was opened, per the procedure.

## Terms used below

- **Wrapper** — the one file in the codebase allowed to talk to an outside company's service.
  Everything else in the product has to go through it. There are three that cost money:
  the AI model provider (Anthropic), the keyword-data provider (DataForSEO), and the email
  sender (Resend).
- **Cost record / cost event** — the note we write saying "this call cost $0.0031". These are
  what the daily spend caps add up.
- **PostHog** — the third-party analytics service where the product's telemetry goes. It draws
  the dashboards. The specs are explicit that it must never be the thing that *decides*
  anything, because it can be down or delayed (main §14.7, "the one boundary to respect";
  constitution invariant 17).
- **Request cache** — a table (`request_cache`) holding the vendor's raw answer, so if the
  job crashes and restarts, we replay the stored answer instead of paying the vendor twice.
- **Spend cap / auto-trip** — the safety valve that pauses the product when a day's spending
  runs away (main §14.5).

---

## Verdict on the flagged concern

**The negative is proved; the positive is not.** The build does stop anyone from importing a
vendor's software kit outside its wrapper, and that lint rule works. But tracing every exit
path out of each wrapper, **five of them spend money and write no cost record at all**, and —
more fundamentally — **no cost record is ever written to our own database**. Every cost record
this card produces is a PostHog analytics event and nothing else, while the spec requires the
spend caps to be computed from our own database. So the caps that pause the product currently
have nothing to read.

Here is the full path-by-path trace, as requested. "Cost record" below means *any* record —
PostHog or database.

| Exit path out of a wrapper | Cost record written? |
|---|---|
| Happy path (vendor answers, we use it) | Yes — PostHog only |
| Throws before the vendor is reached (missing config, missing credentials) | No record — correct, nothing was spent |
| Cache hit (replay) | Yes — PostHog only, correctly at `cache_hit: true` / `$0` |
| Retried step where the first attempt cached its answer | Counted once. Correct. |
| Vendor reached, then HTTP error / rate limit / timeout / network drop | **No record.** Findings 2 and 4 |
| Streaming call cut off partway (tokens generated and billed) | **No record, and the tokens are discarded.** Finding 3 |
| Vendor answered, then our own database write fails | **No record.** Finding 5 |
| DataForSEO returns HTTP 200 whose body reports a task-level failure | **No record, and no cache row.** Finding 4 |
| DataForSEO endpoint added without a price entry | **No record**, and a successful call is turned into a failure. Finding 10 |
| Any path at all, when the PostHog key is not configured | **No record, silently.** Finding 6 |
| Any path, for events still buffered when the server is redeployed | **Lost.** Finding 7 |
| Email (Resend) — every path | No cost record anywhere. Finding 13 (not spec-required) |

## Findings

### [blocker] main §14.7 (final paragraph), §14.5; constitution invariant 17 — cost is recorded only in PostHog; no database counter exists, so the spend caps have nothing to read

**Finding.** The daily spend caps that pause the product when something runs away are supposed
to be computed by our own code from our own database. Nothing in this build writes a cost
figure to the database. The only output of both money-spending wrappers is an analytics event
sent to PostHog.

**Spec requires.** Main §14.7 states it directly: "The §14.5 budget auto-trips read spend from
our own DB counters — PostHog displays cost, our code enforces caps." And: "PostHog is
telemetry and alerting, **not** the control plane… a kill switch must work when PostHog is
down or events are sampled/delayed." The constitution restates this as invariant 17.

**Code does.** `packages/llm/src/client.ts:230` (`emit`) and
`packages/providers/src/seo/index.ts:151,175` (`captureSeoRequest`) are the only places a cost
figure leaves the wrappers, and both go to PostHog. Schema wave 1
(`packages/db/migrations/0000_wave1.sql`) has no spend or cost table — the tables are
`accounts, subscriptions, stripe_events, domains, preview_cache, shopify_conns,
ingestion_jobs, job_steps, ops_flags, request_cache, webhook_events, email_sends,
email_suppressions, notification_prefs, notifications`. Meanwhile the cap *numbers* already
exist and are wired up: `packages/rules/signals.config.yaml:352-372` carries
`hard_cap_usd_per_day: 5.00`, `dataforseo_spend.global_cap_usd_per_day: 50.00`, and
`preview_spend.global_cap_usd_per_day: 10.00`. So the thresholds exist and the meter does not.

**Who owns it.** This is not, strictly, a T0.5 scope violation — the card's scope text names
the PostHog captures and does not name a database counter. The card that *needs* the counter
is **T8.4** (`docs/agent-work-plan.md:364`), which says auto-trips run "from DB counters". That
card is currently unbuildable as written: there are no counters and nothing writes to them.

**Why I am calling it blocker anyway.** T0.5 is the card that fixes the *shape* of every cost
call site in the product for the next eight milestones. `AiGenerationEvent` and `SeoRequestEvent`
(`packages/core/src/contracts/analytics.ts:78-104`) are one-way: they hand a number to
analytics and return nothing. Adding a durable ledger after several hundred call sites are
written against this shape means revisiting all of them. It is dramatically cheaper to decide
now.

**Proposed fix (your decision — do not let a session choose this silently).** Add a second
output alongside the PostHog capture: a `CostLedger` port in `packages/core/contracts` with one
method that appends `(account_id or preview target, vendor, call_type/endpoint, usd_cost,
cache_hit, occurred_at)` to a `spend_events` table, called from the same place in both wrappers
as the PostHog capture. That needs one migration, which the constitution says must arrive in a
schema-wave card. Options: (a) fold it into the next schema wave and make T0.5 emit to both;
(b) leave it to T8.4 and accept that no spend is measurable until M8; (c) something narrower —
a daily rollup counter rather than an event log. My recommendation is (a): the ledger is
append-only, tiny, and it is the only thing that makes findings 2–7 below *detectable* rather
than invisible.

### [major] main §14.7 requirement (1), §14.5 — a call that reaches the vendor and then fails records nothing, in both money-spending wrappers

**Finding.** If we send a request to Anthropic or DataForSEO and something goes wrong *after*
they have started work — their server returns a 500, the connection drops, the request times
out — the wrapper throws and no cost record is emitted. Both vendors bill for work performed,
not for bytes we successfully received. So this is real money leaving with no trace.

**Spec requires.** Main §14.7 requires "every call site goes through one shared instrumented
client wrapper… so no call can escape tracking", and the caps in §14.5 are only as good as the
records they sum.

**Code does.**
- LLM: `packages/llm/src/client.ts:206-217` — `send()` catches, converts to a typed failure and
  `throw`s. The exception propagates out of `callModel` before line 200's `this.emit(...)` ever
  runs. Nothing is captured.
- DataForSEO: `packages/providers/src/seo/index.ts:186-206` — `post()` throws on a connection
  error or a non-2xx status, before the `captureSeoRequest` at line 175.

There is no test covering a cost record on any failure path; the error tests
(`packages/providers/src/seo/seo.test.ts:105`, `:125`) assert the error *class* only.

**Proposed fix.** Emit a cost record on the failure path too, marked as such — e.g. an
`outcome: 'failed'` property with a best-effort cost (for LLM, the input tokens are known from
the request; for DataForSEO, the endpoint's per-task price). Wrap the vendor call in
`try/finally` so the emit cannot be skipped by an exception. Add a test per wrapper asserting a
record exists after a 500 and after a connection drop.

### [major] main §14.7 requirement (1) — a streaming call cut off partway discards the token usage the vendor already billed, and the whole streaming branch is untested

**Finding.** For large requests (anything asking the model for more than 8,192 tokens — which
will include article drafting), the wrapper switches to a streaming call. If that stream is cut
off partway, the tokens generated so far were produced and billed, but the code throws away
everything, records nothing, and the branch has no test at all.

**Spec requires.** As above — every call captured, and §14.5's caps summing real spend.

**Code does.** `packages/llm/src/client.ts:212` —
`await this.anthropic.messages.stream(params).finalMessage()`. The `finalMessage()` promise
rejects on an aborted stream; the stream object's accumulated partial usage is never read. The
test double at `packages/llm/src/client.test.ts:28-44` implements only `messages.create`, so no
test ever enters this branch. The 8,192 threshold is a code constant
(`STREAMING_MAX_TOKENS_THRESHOLD`, line 46) with no spec citation.

**Proposed fix.** Hold the stream object, and on rejection read its accumulated usage before
re-throwing, emitting a partial-cost record. Add a test that aborts a fake stream after a few
chunks and asserts a non-zero cost record.

### [major] main §14.3.6, constitution invariant 20 — DataForSEO's answer is inspected before it is cached, so a failure reported inside a successful HTTP response both loses the cost record and re-bills on retry

**Finding.** DataForSEO reports per-task failures inside an HTTP 200 body. The wrapper checks
for that *before* it writes the answer to the cache. Two consequences: a call that DataForSEO
has already executed and billed leaves no cost record and no cache row (so a retry pays again);
and, strictly, the "write before you process" rule is broken, because parsing and validating the
body *is* processing.

**Spec requires.** Main §14.3.6: the request cache is "**written before the response is
processed** — a crash after the API responded but before downstream processing still finds the
cached response on retry and never re-bills". Constitution invariant 20 restates it.

**Code does.** `packages/providers/src/seo/index.ts:164-170`: `post()` → `extractResult()` →
*then* `writeBeforeProcessing()`. `extractResult` (lines 211-226) throws when the task status
code is ≥ 40000. The test at `seo.test.ts:125` confirms this throws, and asserts nothing about
the cache or the cost record.

**Proposed fix.** Move the cache write to immediately after `response.json()`, storing the raw
envelope, and do `extractResult` on the stored value afterwards — which is also what the LLM
wrapper does correctly (it caches the raw text before validating it). Then emit the cost record
in a `finally`. Add a test asserting that a task-error response still produces a cache row and
a cost record.

### [minor] constitution invariant 20 — if the cache write itself fails after a successful model call, the cost record is lost too

**Finding.** A narrow window, but the same class as findings 2 and 4: if the database hiccups
while storing the model's answer, we have already paid Anthropic, and the code throws before
recording anything.

**Code does.** `packages/llm/src/client.ts:182-200`: `writeBeforeProcessing` is awaited at line
182; `this.emit(...)` is at line 200.

**Proposed fix.** Emit the cost record before the cache write, or in a `finally`. Recording
costs more than caching does, so it should be first.

### [major] main §14.7 — cost tracking is optional at construction and silently disabled without a PostHog key, and nothing in the app wires it up

**Finding.** Both wrappers accept the analytics recorder as an *optional* constructor argument
and call it with a "skip if absent" operator. And the PostHog wrapper itself, if no project key
is configured, throws nothing and records nothing. So a wrapper built without a recorder, or a
production deploy missing `POSTHOG_API_KEY`, spends real money and produces zero cost records —
with no error, no warning, no log line. There is currently no place in the app that constructs
these wrappers, so there is nothing yet forcing the recorder to be supplied.

**Spec requires.** Main §14.7 requirement (1): the shared wrapper exists specifically "so no
call can escape tracking".

**Code does.** `packages/llm/src/client.ts:51` (`capture?:`) and `:231`
(`this.capture?.captureAiGeneration`); `packages/providers/src/seo/index.ts:61,159,175` — same
pattern. `packages/providers/src/posthog/index.ts:52-56` builds no client when the key is
absent, and every capture is `this.client?.capture(...)`. This behaviour is enshrined by a test:
`posthog.test.ts:67`, "captures nothing at all when no project key is configured".
`apps/web/instrumentation.ts` (the app's startup hook) registers the log scrubber and boots the
worker; it does not construct any provider.

**Proposed fix.** Make the recorder a required constructor argument, with an explicit
`NoopCapture` that a caller must ask for by name (so "not recorded" is always a visible choice
in the code, never a default). Separately, fail startup in production if `POSTHOG_API_KEY` is
missing, rather than degrading to silence — the specs' own posture is "degrade to pause, never
to lower quality" (invariant 22). Local dev keeps the silent path.

### [minor] tech §2.1 — buffered cost events are dropped on every deploy

**Finding.** PostHog's library batches events and sends them in the background. Railway sends a
shutdown signal on every deploy. Nothing in the codebase drains that buffer on shutdown, so the
most recent events are lost each time the app redeploys. Harmless for a funnel metric; not
harmless if these events are the only cost record (see finding 1).

**Code does.** `flush()` and `shutdown()` exist on the wrapper
(`packages/providers/src/posthog/index.ts:101-107`) and are called from nowhere outside tests.
Tech §2.1 relies on graceful shutdown: "Railway sends SIGTERM with a grace period on deploy;
Graphile Worker drains gracefully."

**Proposed fix.** Call `flush()` (then `shutdown()`) from the same SIGTERM handler that drains
the job worker.

### [major] main §14.2 — a per-call model override skips the "no aliases" check and prices the call at the wrong model's rates

**Finding.** Each kind of AI call is assigned a model tier — cheap (Haiku) for product
summarising, full-strength (Sonnet) for the persona, drafting and the quality judge. A caller
can override the model per call. That override is applied to the *name* of the model but not to
its *prices*, so the recorded cost is computed from the tier's price list, not the overriding
model's. Overriding a Haiku call with a Sonnet model would record roughly half the real cost.
The override also skips the alias check the environment-variable path performs.

**Spec requires.** Main §14.2: "model IDs are explicit config values (never 'latest' aliases)",
and every artefact stamped with the model actually used. §14.7 requires the cost figure to be
real.

**Code does.** `packages/llm/src/client.ts:118-122`: `modelFor` returns
`{ ...spec, id: request.model }` — new id, old prices, no `ALIAS_PATTERN` check. Contrast
`packages/llm/src/models.ts:62-70`, where the environment override *is* alias-checked. The
mock client repeats the same mistake (`packages/llm/src/mock.ts:74-81`). Nothing uses the
override today, so no cost has been mis-recorded yet.

**Proposed fix.** Either remove `LlmRequest.model` entirely (the tier map plus the env override
already covers what §14.2 and §15 ask for), or route it through a lookup that requires a known,
priced, non-alias model id and rejects anything else. Removing it is cleaner and I would
recommend that; it is your call whether any future card needs per-call model choice — invariant
11 says the quality judge must never be downgraded, which an unchecked override would permit.

### [major] constitution invariant 25 — the "one wrapper per vendor" rule has no teeth for DataForSEO

**Finding.** The rule is enforced by a lint check that bans importing a vendor's software kit
outside its wrapper. DataForSEO has no software kit — it is a plain web address you send a
request to. So nothing stops any file in the codebase from calling
`fetch('https://api.dataforseo.com/...')` directly, bypassing the cache, the price map, and the
cost record entirely. This is precisely the hole the flagged concern is about, and it is in the
mechanism that is supposed to prove the negative.

**Spec requires.** Invariant 25: "Same wrapper rule for DataForSEO (`SeoDataProvider`)". Main
§12.1 requires the vendor to sit behind that interface.

**Code does.** `tools/eslint-plugin-sortiva/rules/no-direct-provider-sdk.js:9-16` lists six
module names — Anthropic, Resend, Stripe, PostHog, Shopify, Google — and no DataForSEO entry,
because there is no module to name. The host string appears only once in the codebase, at
`packages/providers/src/seo/index.ts:42`.

**Proposed fix.** Extend the same lint rule (or add a sibling) to ban the literal string
`api.dataforseo.com` outside `packages/providers/src/seo/`. Cheap, and it closes the last
unguarded vendor.

### [minor] main §14.7 — the "unpriced endpoint" guard loses the cost record and fails a call that already succeeded

**Finding.** If someone adds a new DataForSEO endpoint without adding its price, the code
deliberately throws rather than reporting the call as free. The intent is right. But it throws
*after* the vendor has been called and billed, and *before* the cost record is emitted — so the
guard against under-counting causes an under-count, and turns a successful paid call into a
job failure.

**Code does.** `packages/providers/src/seo/pricing.ts:57-64` throws;
`packages/providers/src/seo/index.ts:167-176` calls it after the vendor call and the cache
write, before `captureSeoRequest`.

**Proposed fix.** Emit the cost record with a `price_unknown: true` marker and a loud log line
rather than throwing at request time, and move the hard failure to startup: validate that every
endpoint in `DATAFORSEO_ENDPOINTS` has a price entry when the module loads.

### [minor] main §14.3.6, §14.3.9 — the AI test double diverges from the real client on caching, cost recording, and the retry rule

**Finding.** `MockLlmClient` is the stand-in used in tests and in the crash-recovery ("chaos")
test runs. It ignores the request cache entirely (so a resumed job appears to pay twice for AI
work that production would replay for free), it emits no cost event at all, and it fails a
schema-invalid response immediately instead of performing the single repair attempt the real
client does. So `attempts` is always 1 and cost is always fresh.

**Spec requires.** §14.3.9's chaos-test assertion is worded only about DataForSEO
("billable-call count equals the number of *distinct* canonical requests"), which the SEO double
does honour correctly. So this is not a letter violation. But the card's own "done when" says
"mock providers account cost", and a double that models a different cost curve than production
will mislead any spend estimate built on it.

**Code does.** `packages/llm/src/mock.ts:70-121`: no `RequestCache`, `cacheHit: false` always,
no `PosthogCapture`, throws on validation failure without the §14.2 retry. Contrast
`packages/providers/src/seo/mock.ts`, which deduplicates on the same canonical key as the real
provider and does accept a capture — that one is a good double.

**Proposed fix.** Give `MockLlmClient` the same optional cache and capture the SEO double has,
and have it perform the single repair attempt so `attempts` means the same thing in both.

### [minor] main §14.5, §14.7 — the DataForSEO prices are unverified, and the spend cap is wrong in the same proportion

**Finding.** The per-call prices used to compute DataForSEO cost are marked in the code as
starting estimates, not checked against a current price list. This was journalled honestly in
`DECISIONS.md` and flagged in the commit message, so it is disclosed rather than hidden — but it
is a live founder action, not a resolved item. If a price is 5× low, the $50/day global cap
effectively becomes $250/day.

**Code does.** `packages/providers/src/seo/pricing.ts:11-16` says "**UNSIGNED**… Verify before
the first production spend." Current values: keyword volume $0.05/call, organic SERP
$0.002/call, ranked keywords $0.011/call + $0.0001/row. The 25× spread between the first two is
worth a sanity check specifically. The caps they feed are in
`packages/rules/signals.config.yaml:352-372`, themselves marked UNSIGNED.

**Proposed fix.** Someone with a DataForSEO account confirms the three prices against the
current price list before the first production call, and separately signs off the three dollar
caps.

### [nit] tech §1.4, main §14.7 — email spend is not tracked anywhere

**Finding.** The email wrapper records no cost. The audit brief lists email as a paid vendor;
the specs do not. Main §14.7's cost taxonomy covers AI and DataForSEO only, and tech §2.1
assumes Resend's free tier ("3k emails/mo covers early volume"). So this is not a spec
violation and I would not change it now. Worth knowing: if email volume passes the free tier,
that spend is invisible to every dashboard and every cap.

**Proposed fix.** None required. If you later want it, the `EmailProvider` interface is the
right place and it is a small addition.

### [minor] tech §4 — the log scrubber's automatic registration misses database connection strings

**Finding.** At startup, every environment variable whose name ends in SECRET, TOKEN, PASSWORD,
API_KEY or KEY is registered with the log scrubber, so its value is blanked out wherever it
appears in a log line. `DATABASE_URL` does not match that pattern, and it contains a password.
A Postgres connection error that echoes the connection string would print the password.

**Code does.** `packages/providers/src/secrets/index.ts:203` — the pattern is
`/(SECRET|TOKEN|PASSWORD|API_KEY|KEY)$/`. `.env.example:12` shows `DATABASE_URL` carrying
credentials inline.

**Proposed fix.** Add `URL$|_URI$|DSN$` to the pattern, or register `DATABASE_URL` explicitly.

## Clean results on the flagged concern and the invariants

These were checked and are correct. Reporting them explicitly, as requested.

**[clean] main §14.7 requirement (3), §14.3.6 — cache hits are free and visible.** A replayed
answer is recorded with `cache_hit: true` and `$0`, so cached work neither inflates the spend
number nor disappears from it. Asserted by a real test that runs the model once across two
client instances and checks the cost of the second is zero
(`packages/llm/src/client.test.ts:122-153`) and by the DataForSEO equivalent
(`packages/providers/src/seo/seo.test.ts:52`).

**[clean] main §14.3.6, invariant 20 — a retried step is billed once, not twice.** For the AI
wrapper, the vendor's answer is written to the cache *before* it is parsed or validated, proved
by a test that feeds back unparseable text and confirms the cache row exists anyway
(`client.test.ts:107-120`). A retried step replays the identical stored answer rather than
re-asking the model — which also means a resumed job cannot get a *different* answer than the
run it is resuming, exactly as the spec argues for. (The DataForSEO side of this has the gap in
finding 4, but the ordinary path is correct and tested.)

**[clean] main §14.2 — the repair attempt is billed per attempt, correctly.** When the model
returns something that fails validation, the wrapper retries once with the error appended, then
raises a typed failure rather than salvaging partial output. Each of the two model calls emits
its own cost record, and the returned result sums them — so a repair loop shows up as two calls'
worth of spend, which is what it is. The design choice that the repair turn gets its own cache
entry (it is a different prompt) is journalled in `DECISIONS.md` and is right: a step that
retries after a validation failure replays both stored answers and fails deterministically for
free.

**[clean] main §14.7 preview attribution rule.** Unregistered visitors previewing a site are
tracked by a plain `target_domain` property and never grouped under that domain — "ten strangers
previewing nike.com is not Nike-the-account costing us money". This is enforced by the *type*
of the attribution value (`packages/core/src/contracts/analytics.ts:26-40`): a preview event has
no field where a domain group could be put, so it cannot acquire one by accident. That is a
better mechanism than a convention, and it is tested on the production code path
(`client.test.ts:174-196`, `posthog.test.ts:29`).

**[clean] invariant 25 for Anthropic, Resend and PostHog.** The lint rule
(`tools/eslint-plugin-sortiva/rules/no-direct-provider-sdk.js`) is real, is wired into
`eslint.config.mjs` at error level with no test-file exemption, and covers direct imports,
dynamic imports, `require`, and TypeScript's import-equals form. It also pre-registers the
Stripe, Shopify and Google entries for cards not yet written. DataForSEO is the exception —
finding 9.

**[clean] invariant 26 / tech §4 — the log scrubber.** Two independent mechanisms (secret-looking
key names plus vendor token shapes, and a registry of literal secret values read from the
environment at startup), applied recursively, cycle-safe, and applied to error messages and
stack traces. The card's "a token never reaches log output" is genuinely proved
(`packages/core/src/observability/scrub.test.ts:68`), including nested fields and stacks. Token
encryption at rest uses a per-row key wrapped by a master key, with key-fingerprint tagging so
retired keys stay readable — matching tech §4, and going slightly beyond it with a rotation
path.

**[clean] main §14.3.6 cache key derivation.** Both wrappers key exactly as specified — AI on
`(prompt version, model id, hash of the rendered prompt)`, DataForSEO on `(endpoint, hash of
canonicalised parameters)` with sorted keys and normalised locale codes, so the same question
asked with the keywords in a different order is one billable read, not two. Tested on both
sides, and the DataForSEO test double keys through the *same* function as the real provider, so
its billable-call count means the same thing.

**[clean] privacy on cost events.** Neither wrapper puts prompt text, article text or product
content into an event; only ids, token counts, costs and flags. Every property passes through
the scrubber before leaving the process.

## Summary for the founder

The card built what it said it built, the tests are real tests rather than restated assertions
(361 pass across the repo, including ones against a live Postgres and a live job worker), and
the two most interesting design calls are honestly journalled in `DECISIONS.md`. The caching,
key derivation, preview-attribution and log-scrubbing work is genuinely solid.

The gap is on the money side, and it is one idea with several symptoms: **the wrappers treat
recording a cost as a side-effect of a successful call, not as an obligation of the call.**
That produces five paths where money is spent and nothing is written down (findings 2, 3, 4, 5,
10), plus two where the record is written and then quietly dropped (findings 6, 7). Underneath
all of them sits finding 1: even when a record *is* written, it goes only to the analytics
service the spec forbids us from making decisions with, so the spend caps have no meter to read
and the card that is supposed to build them (T8.4) has nothing to build on.

Three things I would put in front of you before dependent cards start:

1. **Decide where cost records live** (finding 1). This changes an interface that every future
   call site will use, so deciding it after M0 is much more expensive than deciding it now.
2. **Decide whether failure paths must record cost** (findings 2–5). They currently don't, and
   the fix is small and local while there are no call sites.
3. **Confirm the DataForSEO prices and the three dollar caps** (finding 11). This one needs a
   person with a vendor account, not a code change.

Nothing was fixed. Nothing was changed.
