# Audit — T1.2 "Stripe billing & entitlement", commit `f87f1ce`

Read-only audit. Nothing in `sortiva-lane-a` was modified. Where I needed to
break something to see whether a test would notice, I did it in a throwaway copy
of the repo under my scratchpad and threw it away afterwards.

## How to read this

Every finding is one line of the form
`[severity] §ref — finding / spec requires / code does / proposed fix`,
followed by a plain-language explanation. Nothing here has been fixed; these are
proposals.

Terms I use repeatedly, defined once:

- **Entitlement** — whether an account is allowed to have the product generate
  and publish articles for it. The spec says it is decided by one column in our
  own database (`subscriptions.status`) and never by asking Stripe live.
- **Webhook** — a message Stripe pushes to us when something happens to a
  subscription. Stripe promises to deliver each one *at least* once, and makes
  no promise about the order they arrive in.
- **The ordering guard** — the rule this commit added so that a webhook
  describing older news than we already hold is ignored instead of overwriting
  newer news.
- **`synced_at`** — a column on the `subscriptions` table. What it is supposed
  to mean is one of the findings below.
- **The drain** — the loop that reads stored webhook events out of the database
  and applies them.

---

## Summary

The core of this card is right, and several of the things the building session
asked me to attack turned out to be genuinely sound — I say so explicitly below
rather than staying silent about them. The commit is honest about its own gaps:
the decision journal already records the ones the session knew about, including
the two the founder has since ordered fixed, and it does not anywhere claim the
Stripe test-clock criterion was met (I checked; it is recorded as **not met**,
which is correct).

What I found that the session did not:

- The single-writer rule it depends on is **not enforced by anything**. I added a
  second writer to that column in a copy of the repo and all 464 tests passed.
- The per-account lock it hoped was engaged in production is **not engaged in
  production**. Only tests pass it a connection pool.
- Two webhooks stamped by Stripe with the same second do not "last-writer-win" —
  the winner is decided by the **alphabetical order of a random Stripe event
  id**. I proved this against real Postgres.
- There is a path where a merchant **pays and never becomes entitled, with no
  automatic repair**: the row is never created, and the nightly repair job only
  looks at rows that already exist.

And on the change the founder has already commissioned: **splitting Stripe's
timestamp into its own column fixes the `synced_at` problem but does not fix the
same-second problem**, because that one is about the resolution of Stripe's
clock, not about which column stores it. Detail in finding 4.

## Findings

### 1. Nothing stops a second writer to `subscriptions.status`

`[major] main §4.2, tech §3, invariant 16 — the "single writer" rule is enforced
by convention only / spec requires that the Stripe webhook worker is the sole
mutator of `subscriptions.status` / the code has exactly one writer today but no
test, lint rule or database constraint prevents a second / add a source-scanning
test in the same style as the existing Stripe call-site test, and consider a
database-level guard.`

The whole design rests on one claim: the only thing that ever changes an
account's billing status is the worker that processes Stripe's webhooks. If a
future card writes to that column from somewhere else — a settings screen, an
admin script, a "reactivate" button — entitlement stops being a mirror of Stripe
and starts being a second opinion, and the two will disagree.

The session wrote a test that proves no Stripe *API call* escapes the four
sanctioned files (`packages/core/src/billing/stripeCallSites.test.ts`). I
verified that test is real: I planted a Stripe call in an unrelated file and it
failed immediately, naming the offending file. That test is good and should stay.

But it guards calls, not writes. I planted a second writer —
`UPDATE subscriptions SET status = 'active'` — in
`apps/web/app/api/account/_lib/load.ts`, a file that has nothing to do with
billing, and ran the **entire** test suite: 31 files, 464 tests, all passed. The
invariant is currently protected by nobody noticing in review.

Today there genuinely is only one writer. I grepped every non-test TypeScript and
SQL file: the sole `INSERT`/`UPDATE` against that table is `applyWrite` in
`apps/web/app/api/billing/_lib/store.ts:118`. So this is a defence-in-depth gap,
not a live bug — but it is the single most load-bearing assumption in the card,
and it is the one thing with no automated defence.

Proposed fix: a test that walks every source file looking for SQL or ORM writes
naming the `subscriptions` table and fails unless the file is on a one-item
allowlist. The pattern already exists in this very commit and is proven to work.

### 2. The per-account lock never engages in production

`[major] main §14.3.3, invariant 18 — all work for one account must serialise
under a per-account lock / spec requires every worker to serialise account work
under `pg_advisory_xact_lock(account_id)` or equivalent / the billing write takes
the lock only when a connection pool is handed in, and no production code path
hands one in / pass the pool from the composition root, or drop the read-then-
write pattern that needs the lock.`

The session flagged this as something it was unsure of. It is confirmed: the lock
does not run in production.

The mechanics. `makeBillingStore` in
`apps/web/app/api/billing/_lib/store.ts:75` wraps the status write in
`withAccountLock` **only if** an optional `pool` was passed:

```
return options.pool ? withAccountLock(options.pool, write.accountId, run) : run()
```

Every production caller passes nothing. `apps/web/app/api/webhooks/stripe/_lib/route-handler.ts`
builds the live route as `makeStripeWebhookRoute()` — no options — and the
nightly job in `.../tasks.ts` calls `billingWorkerDeps()` — no options. Only the
two integration test files pass `pool: harness.pool`. So in production the write
is a bare read-then-write with no serialisation; in tests it is locked. The tests
exercise a code path production never takes.

Does it matter? The database-level ordering guard (the `WHERE` clause) still
protects the *stored status* from being rolled back, so the damage is bounded.
What is unprotected is the read that happens just before the write —
`applyWrite` reads the current status so it can tell whether the status
*changed*, and that decision drives the analytics events and (once real emails
exist) the payment-failed email. Two events for the same account processed
concurrently can both read the same "before" value and both report a change.

And concurrency here is real, not theoretical. The receiver fires the drain
without waiting for it (`void drainStripeEvents(deps)`, receiver.ts), and the
drain's `claimUnprocessed` does not actually *claim* anything — it is a plain
`SELECT ... WHERE processed_at IS NULL` with no row locking. Two webhooks
arriving milliseconds apart start two drains that select the same rows and
process them at the same time.

Proposed fix: two independent options, either sufficient — (a) have the
composition root pass the pool so the lock engages, or (b) make `claimUnprocessed`
a real claim (`FOR UPDATE SKIP LOCKED`, or mark-then-process) so two drains
cannot pick up the same row. I would do both. This is a decision, not a
mechanical fix, so I have only proposed it.

### 3. A merchant can pay and never become entitled, with no automatic repair

`[major] main §4.2 — the checkout handler can consume the only event that
creates a subscription row and leave no row and no trace / spec requires
`checkout.session.completed` to attach the customer and subscription to the
account, and the nightly reconciliation to repair rows webhooks left wrong / when
Stripe answers "no such subscription", the event is marked processed and no row
is written; the nightly job only scans rows that already exist, so nothing ever
repairs it / do not mark an unresolved event processed, and alert on it.`

The path, in plain terms. When a merchant finishes paying, Stripe tells us "this
checkout session completed" — but that message does not describe the
subscription (no status, no price, no renewal date). So the worker calls Stripe
back once to read it. That call is fine and I discuss it separately in finding 8.

If that read comes back "no such subscription", the worker returns an
`unresolved` outcome — and the drain marks the event processed anyway, on the
reasoning that replaying it will not help
(`packages/core/src/billing/processing.ts`, the comment at the end of
`drainStripeEvents`). The merchant now has: money taken by Stripe, no
`subscriptions` row, and therefore no entitlement. The nightly reconciliation
cannot help, because it scans `subscriptions` for stale rows and there is no row.
Nothing else in the system will ever look at this account again.

I proved the end state against real Postgres. With Stripe answering "not found"
for the subscription named in the checkout event: stored status `null`, the event
marked processed `true`, and `0` rows for the reconciliation to scan.

How likely is "no such subscription" for a subscription Stripe just created?
Rare, but there is one realistic trigger: a **key/mode mismatch** — production
receiving live-mode webhooks while holding a test-mode secret key, or the reverse
in staging. Stripe answers `resource_missing` for every object in the other mode.
That is a launch-day configuration mistake, exactly the kind that happens once,
and it would silently swallow every new subscriber until someone noticed
manually. Given no Stripe credentials exist yet, this configuration has never
been exercised.

There is a smaller sibling of the same hole. A `customer.subscription.updated`
that arrives *before* the checkout event has attached the Stripe customer to the
account cannot find its account, so it is dropped and marked processed. I
confirmed this too (no row written, event marked processed). Today this
self-heals, because the checkout event's live read picks up the current state
moments later — but it self-heals only via the read that finding 8 discusses, and
not at all if that read fails.

Proposed fix: leave `unresolved` events unprocessed (or move them to a dead-letter
record) so they are retried and visible, and emit an alert. The existing
`dlq_entry_created` telemetry event in main §14.7 is the natural home. Separately,
the nightly reconciliation should have a way to notice an account that has a
Stripe customer id but no subscription row.

### 4. Same-second events: the winner is the alphabetically-last event id

`[major] main §4.2, §14.3.8 — two Stripe events stamped in the same second can
leave the wrong status stored / spec requires out-of-order delivery to be
handled; it does not specify how / the ordering key is Stripe's `created`
timestamp, which has one-second resolution, and ties are resolved by whichever
event happens to be applied last — within one batch, by `ORDER BY event_id`,
which is alphabetical order of a random string / stop ordering on the timestamp
alone: re-read the subscription from Stripe on every subscription event and stamp
it with the read time.`

The session asked an auditor to argue about its choice to let equal timestamps
both apply. Having tested it, my view is that the choice is defensible but the
premise underneath it is not: **a one-second timestamp is not a valid ordering
key for Stripe events**, and no tie rule rescues it.

Two probes against real Postgres:

- Two subscription events both stamped second `2000`, one saying `active` and one
  saying `past_due`, delivered in separate batches: the **last one to arrive
  wins**, regardless of which described newer state. I arranged for the older
  news to arrive last and the row ended on the older news.
- The same two events arriving in one batch: the drain sorts by
  `created ASC, event_id ASC`, so the winner is whichever event id sorts last
  alphabetically. `evt_zzz` beat `evt_bbb`. Stripe event ids are random, so this
  is a coin flip that *looks* deterministic.

What breaks in practice. Stripe commonly emits several events for one
subscription inside a single second — at checkout, and again on every renewal and
every dunning retry. If two of them describe different states (Stripe flipping a
subscription from `incomplete` to `active` on immediate payment, for instance),
the row can settle on the wrong one. The consequences are asymmetric: settling on
a stale `active` costs us one day of generation on an unpaid account; settling on
a stale non-`active` locks out a merchant who has just paid. Recovery is the
nightly reconciliation, so **up to 24 hours**. The plan screen's optimistic
"setting up your account…" interstitial (ui §2.3) polls for 30 seconds and then
shows "taking longer than expected", which is what the merchant would see.

Choosing `<` instead of `<=` (reject ties) does not help — it would make ties
resolve to "first arrival wins", equally arbitrary, and it would additionally
break the reconciliation's deliberate `max(now, stored)` clamp, which relies on an
equal timestamp being applied. So `<=` is the better of the two available
choices, and the session's reasoning for it is sound as far as it goes.

**This is the finding most relevant to the card already in flight.** Moving
Stripe's timestamp into its own dedicated column restores `synced_at`'s meaning
(finding 5) but leaves this untouched, because the problem is the one-second
resolution of `created`, not which column holds it. If that card ships and
this is not addressed, the same-second race survives the fix and will look
fixed.

Proposed fix, in preference order: (a) treat every `customer.subscription.*`
event as a signal to re-read the subscription from Stripe and stamp it with the
*read* time — this is what the checkout handler already does, it makes ordering
irrelevant entirely, and it costs one non-billable API call per subscription
webhook in a background worker where invariant 16 permits calls; or (b) add a
monotonic tiebreaker of our own (the `stripe_events` insertion sequence) so ties
resolve to arrival order deterministically rather than by event id. Option (a) is
also what Stripe's own guidance recommends. Either is a design decision.

### 5. `synced_at` now means two different things at once

`[minor] main §13, tech §3 — the column repurposed to hold Stripe's clock also
still drives the staleness scan, and the two readings conflict / spec lists
`synced_at` on the `subscriptions` table and tech §3 requires the nightly job to
"re-fetch any subscription whose `synced_at` is >24h stale" / the column now
holds Stripe's timestamp for the state, so every healthy subscription looks
permanently stale and the nightly job re-fetches the whole customer base every
night, capped at 500 / restore the original meaning and give Stripe's timestamp
its own column — which is the card already in flight.`

The session repurposed the column deliberately, journalled it, and flagged it for
scrutiny. I agree with its judgement that it is *safe* — nothing today reads
`synced_at` for any other purpose, and I confirmed by grep that the only readers
are the reconciliation scan and the ordering guard itself. But it has two
consequences worth stating plainly:

**Consequence 1, live today.** Under the original meaning ("when we last wrote
this row"), a healthy subscription is refreshed the moment its row goes 24 hours
untouched — the job is a small repair sweep. Under the new meaning ("when Stripe
last changed this subscription"), a healthy monthly subscription's stamp is
frozen for a month, so *every* subscription is stale *every* night. The nightly
job becomes a full re-sync of the customer base, capped at 500 accounts per run
(`RECONCILE_BATCH_SIZE`). Past 500 paying accounts the "no row goes unchecked for
more than 24h" guarantee quietly stops holding — it degrades into a rotating scan
rather than failing loudly. That is a growth cliff, not a bug, and it is a long
way off, but it is invisible.

**Consequence 2 — the specific question I was asked: what breaks if a later card
writes the current time to `synced_at`?** This is the dangerous one, and it is
worse than "the staleness scan gets confused". Writing `now()` sets the ordering
guard's floor to the present moment. Every subsequent webhook carries a Stripe
timestamp from the past, so **every subsequent webhook is discarded as stale** and
the account's billing status freezes at whatever it held. A failed payment would
not pause generation; a recovered payment would not resume it. The only repair is
the nightly job — up to 24 hours late, and only if `synced_at` has not been
overwritten again in the meantime. The failure is silent: no error, no log, just
a status that stops moving.

Nothing warns a future author about this. The schema comment at
`packages/db/src/schema/accounts.ts:41` still describes the original meaning
("`synced_at` drives the nightly reconciliation of any row stale > 24h"). The new
meaning is documented in `DECISIONS.md` and in comments inside the billing
module — neither of which the next person to touch the schema will be reading.

The in-flight fix (a separate column) is the right one and closes both
consequences. I would add: when it lands, the ordering column should be named for
what it is (`stripe_event_at`, say) and the schema comment should say in one line
that writing `now()` to it disables the guard.

### 6. `incomplete` is stored as `incomplete_expired`

`[minor] main §13 — a recoverable Stripe state is recorded under the name of a
terminal one / spec fixes the stored column to four values: active, past_due,
canceled, incomplete_expired / Stripe's `incomplete` ("first payment not finished,
may still succeed") is written as `incomplete_expired` ("first payment failed
permanently") / add the fifth value, which is the card already in flight.`

The session said it was least comfortable with this one. My assessment: it is the
*least* harmful of the four things it asked me to attack, and it does not affect
entitlement at all — both values are non-`active`, so both gate identically, and
read access is unaffected either way.

Where it bites is human and downstream. A founder or support agent reading the
database sees "expired" for an account whose payment may still complete within
the next 23 hours, and would reasonably tell that merchant their signup failed.
And the funnel event is worse: `announce()` in `processing.ts` fires
`subscription_canceled` for both `canceled` **and** `incomplete_expired`, so an
account whose card is still being authorised is counted as churn in the §16
metrics from the moment its subscription is created. Adding the fifth enum value
fixes the storage; the analytics mapping needs looking at separately, and the
in-flight card will not necessarily catch it.

Two smaller mapping judgements in the same function
(`packages/core/src/billing/provider.ts`), both defensible, both worth a
conscious nod: `trialing → active` (we sell no trials, so it should never appear;
if it does, treating it as entitled is the generous choice), and
`paused → canceled` (Stripe's paused-collection state, which also fires the
`subscription_canceled` funnel event and shows the merchant a cancelled banner
for a subscription they did not cancel). Unknown future Stripe statuses default to
not-entitled, which is the safe direction and is a good call.

### 7. The entitlement helpers have no consumer yet — the link is unproven

`[minor] main §4.2 — `isEntitled` and its wrappers are correct but nothing in
production calls them / spec requires the scheduler to check entitlement at
dequeue and auto-publish/export to check it API-side / six routes in the frozen
route table are marked as requiring entitlement, none of them exists yet, and
`billingGate`/`isEntitled`/`assertEntitled` are referenced only by tests / no fix
needed now; the dependent cards must be told to use these functions rather than

I grepped: outside test files, `isEntitled`, `billingGate`, `entitlementStatus`
and `assertEntitled` have zero callers. The six routes marked
`requiresEntitlement: true` in `packages/core/src/api/routes.ts` (scheduling an
opportunity, generating a recommendation, adding a calendar topic, approving,

The one thing that increases the risk of drift: the account API response already
ships the raw `status`, `cancelAtPeriodEnd` and `currentPeriodEnd` to the client

the dashboard banner is to compare those three fields by hand, which is exactly
the "second opinion next to the source of truth" that `billingGate`'s own comment
warns against. Worth an explicit instruction in the handoff.

### 8. A live Stripe read stamped with a stale timestamp

`[minor] main §4.2 — the checkout handler reads fresh data from Stripe but labels
it with the webhook's timestamp / spec is silent on this; the reconciliation path
in the same commit does the opposite / `handleCheckoutCompleted` stamps the live
read with the event's `created`, while `reconcileSubscriptions` correctly stamps
its live read with the fetch time / stamp both with the fetch time.`

Two code paths in this commit do the same thing — call Stripe, get the current
subscription, write it down. They disagree about what timestamp to attach.
`reconcile.ts` uses the moment of the fetch, with a deliberate comment explaining
that a fresh read is by definition the newest view that exists.
`processing.ts`'s checkout handler uses the webhook's `created` instead, which
can be minutes old if the drain was backed up.

The effect is small and self-correcting, but real in both directions: a fresh
read can be discarded as stale (safe — the stored state is genuinely newer), or a
genuinely older event created between the webhook and the read can overwrite the
fresh read (briefly wrong; corrected by the next event or the nightly job).
Making the two paths agree costs one line and removes a discrepancy that will
confuse whoever reads this next.

### 9. Nothing schedules the drain, and cron is off entirely today

`[minor] tech §3 — webhook processing has no scheduled backstop / spec requires
200-then-process-async and a nightly reconciliation / the drain runs only when
another webhook arrives, the `stripe_event_drain` task is registered but is not in
the crontab, and the worker keeps cron disabled until every scheduled task has a
handler — which will not be true until several other lanes land / add the drain
to the crontab.`

The session journalled the in-process drain as a known weakness. Two additions
from my reading:

`stripe_event_drain` exists as a registered task in
`apps/web/app/api/webhooks/stripe/_lib/tasks.ts` but appears nowhere in
`packages/jobs/src/runtime/crontab.ts`, and nothing enqueues it. So if a drain
fails partway — Stripe unreachable, database blip — the unprocessed events sit
until the next inbound webhook happens to trigger a new drain. In practice Stripe
sends several events per subscription change so this usually self-corrects within
seconds, but it is luck rather than design.

Second, and worth the founder knowing as an as-shipped fact rather than a defect:
the worker enables cron only once *every* task named in the crontab has a
registered handler (`packages/jobs/src/runtime/bootstrap.ts`), and most of those
tasks belong to cards not yet written. **So the nightly reconciliation does not
currently run at all.** Every "the nightly job repairs it" reassurance in this
audit — including my own — is conditional on that changing before launch. The
session's journal notes this; it is easy to miss.

### 10. The payment-failed email dedupe is proven by a test production does not share

`[minor] main §4.2, tech §1.2 — the "one email per dunning episode" guarantee is
established by the test harness, not by the wiring / spec requires one
payment-failed email, deduped on (account, type, dedupe key) / the notification
emitter is a placeholder constructed fresh on every webhook request, so its
in-memory dedupe cannot span requests; the test that proves single-sending reuses
one instance / no fix now — flag it for the card that builds real notifications.`

The dedupe *key* this card derives is right: it is keyed on the subscription plus
the billing period, so Stripe's retry schedule produces one email per dunning
episode rather than one per retry attempt. That logic is the part T1.2 owns and
it is correct.

But `billingWorkerDeps` does `new StubNotificationEmitter(capture)` on every
call, and every webhook request calls it. Nothing survives between requests. The
test passes because the harness holds a single emitter for the whole test. When
the real emitter lands it will dedupe in the database on a unique constraint and
the guarantee will hold — but until then, nobody should read the passing test as
evidence that the guarantee holds in production. Nothing sends email today, so
this is currently inert.

## The four things the building session asked me to attack

**1. A second writer to `subscriptions.status`.** There isn't one today — I
checked every non-test source and migration file, and the only write is the
guarded upsert in the billing store. But nothing prevents one, and I proved that
by planting one and watching all 464 tests pass. See finding 1.

**2. The ordering guard.** The guard itself is real and well tested — I removed
the `WHERE` clause from the SQL and a test failed immediately and specifically.
The `<=` tie rule is the better of the two available options and the session's
reasoning is sound. But the underlying ordering key is not sound: same-second
ties are resolved by alphabetical event id, and I demonstrated a wrong final
state. The `checkout.session.completed` racing `customer.subscription.updated`
case works today, but only because the checkout handler re-reads from Stripe; the
racing event itself is silently dropped. The per-account lock does **not** engage
in production — the session's suspicion was correct. Findings 2, 3, 4.

**3. The entitlement read path.** **Clean.** Entitlement is `status === 'active'`
and nothing else. There is no date comparison anywhere — I confirmed by reading
and then by injecting one into `isEntitled`, which broke six tests across two
files. The deliberate comment explaining *why* it is not a date comparison is
correct: a subscription cancelled at period end stays `active` in Stripe until
the period actually ends, so re-deriving the end date locally could only ever
disagree with the source of truth. Read access is genuinely never revoked, tested
against real Postgres for all three dead states. The unproven half is that no
entitlement-gated route exists yet to check — finding 7.

**4. The status mapping.** Real but the least serious of the four. It cannot
affect entitlement, only human interpretation and the churn metric. Finding 6.

## The other things I was asked to verify independently

**Invariant 16, in full — clean, with the two caveats above.** Entitlement comes
from the local row only. No Stripe call sits in any request path: the two payment
routes call Stripe to *create* a hosted Checkout or Portal link, which §4.2
mandates and the card's own done-when sanctions, and neither reads or writes
entitlement. The scheduler does not exist yet, so "no Stripe call at dequeue" is
true but untested. Billing state gates generation and publishing only, and
`billingGate` returns `readAllowed: true` unconditionally with a type that makes
it impossible to return anything else. **No card form exists anywhere** — I
grepped for Stripe Elements and card-field names and found nothing; there are no
UI components in this commit at all. The cap string
"Up to 1 article per day, quality permitting" is held by an inline snapshot and
asserted a second time case-insensitively.

**Invariant 23 — clean.** The plan surface carries no denominator, no "x of y",
no monthly total, and no price, and a test asserts all four.

**Invariant 24 — clean.** I compared each billing string against Appendix A
character by character. The cap line matches. The three cancellation facts match
Appendix A's sentence exactly, stored as three separate sentences rather than one
string — they are identical when joined, and splitting them lets the settings
card render them as three lines, which ui §9.4 wants. The payment-failed banner
and the "no charge was made" note are not Appendix A rows, so verbatim does not
bind them; both match the wording in main §4.2 and ui §2.3 anyway.

**The one Stripe call closest to bending the rules — permitted, and I would keep
it.** When the merchant finishes paying, the worker calls Stripe once to read the
subscription. Main §4.2 forbids a Stripe call "in a request path or at scheduler
dequeue"; a webhook worker is neither. And it is close to necessary: §4.2 assigns
`checkout.session.completed` the job of attaching the *subscription*, but the
checkout payload names the subscription without describing it, and §4.2's event
list deliberately omits `customer.subscription.created`, which is the event that
would otherwise carry the description. Without the read, a merchant who has just
paid holds no row and no entitlement until Stripe's next subscription event —
potentially a month.

**What happens to a merchant who has paid if Stripe is unreachable at that
instant** — this is the important half of the question, and the answer is
different depending on how Stripe fails. A network error, timeout or 5xx throws,
which aborts the drain *before* marking the event processed, so the event is
retried on the next drain — correct behaviour, though "the next drain" has no
schedule (finding 9). A `resource_missing` response returns null, the event is
marked processed, no row is written, and nothing repairs it, ever (finding 3).
That asymmetry is the defect: the recoverable failure is handled correctly and
the unrecoverable-looking one is treated as final when it is most likely a
configuration mistake.

**`synced_at`'s changed meaning — safe today, with a specific silent failure if a
later card writes `now()` to it.** Finding 5.

**Are the tests real?** Yes, and the session's claim to have mutation-checked two
guards holds up. I re-ran the mutations myself rather than taking its word.
Deleting the SQL ordering guard fails exactly the test named for it. Planting a
Stripe call in an unrelated file fails the call-site test with the file named.
Turning entitlement into a date comparison fails six tests. The call-site test
even contains its own anti-vacuity check, asserting it can still see the four
sanctioned call sites — which is a good habit. The integration tests really run
against Postgres rather than skipping: 9 and 14 tests respectively, and I watched
them execute. Total suite: 464 tests, all passing.

One caveat on the read-access tests: they assert that `GET /api/account` returns
200 for `canceled`, `past_due` and `incomplete_expired` accounts, which it does —
but nothing in that code path checks billing state at all, so the test cannot
fail today. That is not a criticism; it is a regression guard aimed at a future
card, and it will do its job the day someone adds a gate in the wrong place.

**The Stripe test clock — correctly reported as outstanding, and not quietly
claimed anywhere else.** I searched the docs, the journal, the commit message and
the work plan. The decision journal records the criterion as **not met**, names
the four specific things that stay unproven until credentials exist, and says the
test clocks must be re-run before anything ships to a paying merchant. The work
plan's own line is unchanged. Nothing overstates it.
